# Reston Hiring Map v3 (Openings) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put real job openings on Eric's map, let him add employers found through them, apply from a job in minutes, and see a three-item daily plan.

**Architecture:** The page stays a single built HTML file made from `src/parts/*`. New parts read a `jobs` collection from the artifact's `db` capability (localStorage fallback). Claude fills that collection only when Eric says "refresh my map", by following `docs/REFRESH.md` and using pure Python helpers in `src/refresh/`. No AI call runs inside the page.

**Tech Stack:** Vanilla JS parts registered with `PARTS.push(function (app) {...})`, three.js r128, Python 3 standard library, Playwright tests with the CDN stub, `python3 -m unittest`.

**Spec:** `docs/superpowers/specs/2026-11-10-openings-design.md`. Read it first. Section numbers below ("spec 4.4") point into it.

## Global Constraints

- Work in `/home/user/reston-hiring-map/reston-hiring-map` (remote `NoLipLearning/MapJob`, branch `main`). Build: `cd src && python3 build4.py`. Serve from the project root: `python3 -m http.server 8765`. Every test defaults to `http://localhost:8765/reston-hiring-map.html`; kill stale servers on other ports before trusting a pass.
- A part talks to the core only through `app` (see the "Part API" block in `src/parts/00-core.js`). A part edits only its own files unless its task lists another file.
- Refresh is on demand only. Nothing is scheduled.
- LinkedIn and Handshake are never fetched, logged into or scraped. Never change a User-Agent or otherwise disguise a request to get past a block; report the block.
- Nothing is invented. `clearance` and `entry` come only from posting text; otherwise `unknown`, shown as "not stated".
- A refresh never changes a job's `status`.
- Refresh budget: at most 28 Indeed searches, 25 `get_job_details` calls, 15 web searches.
- UI rules from `BUILD-PLAN.md` section 0: at most 3 actions per row, no red, no growing counters, the word "Applied" (never "Submitted"), 10-second undo for removals, real buttons, 44px touch targets on touch, visible focus.
- All posting text is escaped with `app.esc`. Links render only when the URL parses with protocol `https:`, with `rel="noopener noreferrer"`.
- When `claude.use("db")` is missing or resolves `null`, each part falls back to localStorage and shows one line saying so.
- Commit after every task. Push after every phase.

## Review Focus

1. A posting whose text never mentions clearance: the job must show "Clearance not stated" and score `clearance = 0.5`, not be treated as no-clearance. (Task 2 and Task 5 tests.)
2. The same job returned by two refreshes, or by Indeed and a careers page: one document, `firstSeen` kept, `status` kept. (Task 2 `test_id_is_stable`, Task 4 runbook check.)
3. A job Eric dismissed that is still live: it must stay dismissed after a refresh. (Task 4 dry-run check, Task 5 test.)
4. A saved LinkedIn link with no pasted text: the job stays visible with "Details not added yet", and no fetch of linkedin.com happens. (Task 6 test.)
5. Posting text containing HTML or script: rendered as text. (Task 5 test `escapes posting text`.)

**Interfaces (all pure, no network):**
- `job_id(source: str, raw: dict) -> str`. `indeed-<job_id>`, `usajobs-<control number>`, `web-<first 12 hex of sha1(url)>`.
- `norm_name(name: str) -> str`. Lowercase; strip punctuation, a leading "the", and the suffixes `inc`, `llc`, `corp`, `corporation`, `co`, `ltd`.
- `classify_clearance(text: str) -> "none" | "sponsor" | "required" | "unknown"`
- `classify_entry(title: str, text: str) -> "yes" | "maybe" | "no" | "unknown"`
- `match_employer(job: dict, employers: list[dict]) -> str | None`. Order from spec 4.5: exact `norm_name`, then alias, then within 150 m plus a shared word of 4 or more letters.
- `parse_posted(text: str, today: date) -> str | None`. Handles `YYYY-MM-DD`, `Posted 3 days ago`, `Just posted`, `30+ days ago` (returns `None`).

`keywords.json` holds the phrase lists. Required entries: `clearance.required`: "active secret", "active top secret", "ts/sci", "must possess a clearance", "clearance required"; `clearance.sponsor`: "ability to obtain", "able to obtain", "eligible for a clearance", "will sponsor", "clearance sponsorship"; `clearance.none`: "no clearance required", "public trust", "background check only"; `entry.yes`: "entry level", "entry-level", "recent graduate", "0-1 years", "0-2 years", "no experience required", "gs-5", "gs-05", "gs-7", "gs-07"; `entry.no`: "5+ years", "7+ years", "10+ years", "senior", "director", "manager", "principal", "lead". Precedence: `required` beats `sponsor` beats `none`; `no` beats `yes`; a title hit in `entry.no` wins outright.

### Task 3: fit score (Opus)

**Files:** Create `src/refresh/score.py`, `src/refresh/test_score.py`.

**Interfaces:**
- Consumes: job dicts shaped like spec 4.1; `routes.json` (`bestMinutes` per `empId`).
- Produces: `score(job: dict, profile: dict, minutes: float | None) -> tuple[int, list[str]]` returning `(fit, fitWhy)`; `commute_score(minutes: float) -> float` with bands `<=15: 1, <=25: .8, <=35: .6, <=45: .4, <=60: .2, else 0`; `estimate_minutes(miles: float) -> float` = `miles * 2.4`.

Formula and weights are exactly spec 4.4. `role` = `min(1, (2 * title_hits + desc_hits) / max(4, n_terms))` over lowercase whole-word matches of the profile's `keywords_for_job_matching` plus `target_roles_implied`.
